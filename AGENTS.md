# alpha-wiki-creator Agent Instructions

Alpha-Wiki plugin repository and release-hardening workspace.

This repository uses Alpha-Wiki as its durable markdown memory layer.

- **Preset:** software-project
- **Overlay:** none
- **Wiki dir:** `wiki/`

## Start Here

1. Read `wiki/graph/context_brief.md` before substantial project work.
2. Use the wiki to recover project purpose, boundaries, contracts, decisions, risks, and gaps.
3. Cite source wiki pages when an answer or implementation decision depends on project memory.
4. Run `python3 .alpha-wiki/run.py -m tools.status --wiki-dir wiki` when the current state is unclear.

## Mutability

- `raw/**` is source evidence. Do not rewrite it during normal agent work.
- `wiki/**` except `wiki/graph/**` is maintained markdown memory.
- `wiki/graph/**` is generated by deterministic tools. Never hand-edit it.
- `.alpha-wiki/config.yaml` is the only page-schema and cross-reference source of truth.
- `AGENTS.md` is the only human-readable project agent contract. Change it deliberately.
- `.claude/**` and `.codex/**` are optional runtime adapters, not competing project contracts.
- Preserve bidirectional wikilinks and run lint after wiki edits.

## Canonical Documents

- Maintain product specifications, contracts, decisions, and standards in place. Search the configured canonical set before creating another document.
- Use `docs/roadmap-execution.md` as the only active product roadmap and backlog. Dated plans and audits are supporting evidence, not competing priorities.
- A canonical document change and its `wiki/log.md` record are one change. Neither may claim the other changed when it did not.
- Create a new canonical document only when no existing document can own the lifecycle. Register it through ingest or an explicit `document-register` entry.
- Keep research, raw evidence, and temporary analysis outside the canonical set until accepted. Do not promote dated working notes into standards by implication.
- Before commit, run `python3 .alpha-wiki/run.py -m tools.document_worker check --root . --config .alpha-wiki/config.yaml`.
- Keep canonical documents, immutable evidence, working candidates, and generated views distinct. Wiki summarizes canonical sources; it does not create a second specification.
- Use `belongs_to` for one ownership parent, not for every dependency. Keep cross-links and decision authority separate from that hierarchy.
- For existing-document maintenance, use `document_worker plan`; bind repository sources through `source_file` or `source_files`. Prepare bounded reviewed JSON edits and run `document_worker apply`. See `docs/quickstart.md` (Maintain Existing Documents).
- Compaction removes redundant prose, not requirements, contracts, risks, open questions, or provenance. Resume an interrupted apply with the same plan and edits; never discard its pending transaction to claim success.
- Hooks and status checks do not imply a continuously running author. Do not launch an LLM from every tool hook or rewrite unchanged documents.
- The controller verifies the full requested outcome, governance/lint and cited retrieval before closing the task. A checkpoint alone is not acceptance.

## Engineering Writing

- Use short technical statements; remove filler and duplicate explanations.
- Keep purpose/scope, behavior/interface, acceptance/evidence, gaps and sources
  only where useful. Preserve required schema sections and frontmatter.
- Prefer compact tables or flow/code notation when clearer than prose. Link
  shared context instead of copying it. Maintain existing document owners.
- Preserve requirements, exceptions, exact diagnostics, identifiers, units,
  uncertainty and provenance. Never shorten away an unresolved question.
- Review authorized edits once for redundancy and meaning. Do not rewrite
  unchanged files, frozen evidence or historical records merely to shorten them.
- Give helpers bounded context and this writing standard; require result,
  evidence, checks, gaps and terminal status, not raw transcripts.

## Agent Workflows

Claude uses `/alpha-wiki:<operation>`; Codex uses
`$alpha-wiki:<operation>`. Both follow this contract and the same config.
Claude loads it through the native `.claude/CLAUDE.md` import adapter.

Return the result and decisive evidence concisely in the user's language.
Read relevant sources, preserve exact diagnostics, and stop when acceptance
passes. Reuse checks while their inputs match. Release blockers require an
applicable requirement, observed failure, affected step, and corrective action.
Use existing release rules; do not invent secrets, signing, or approval chains.

Preferred plugin invocations use the `alpha-wiki` namespace:

- `$alpha-wiki:init`
- `$alpha-wiki:doctor`
- `$alpha-wiki:ingest`
- `$alpha-wiki:query`
- `$alpha-wiki:lint`
- `$alpha-wiki:evolve`
- `$alpha-wiki:status`
- `$alpha-wiki:spawn-agent`
- `$alpha-wiki:render`
- `$alpha-wiki:review`
- `$alpha-wiki:rollup`
- `$alpha-wiki:audit-project`
- `$alpha-wiki:orchestrate`
- `$alpha-wiki:backlog`
- `$alpha-wiki:handoff`
- `$alpha-wiki:release-check`


Standalone compatibility skills use `$alpha-wiki-<operation>` only when the
plugin surface is unavailable. Do not install both surfaces together.

Project-local deterministic tools remain the source of truth:

```bash
python3 .alpha-wiki/run.py -m tools.doctor --project-dir . --platform codex --refresh
python3 .alpha-wiki/run.py -m tools.status --wiki-dir wiki
python3 .alpha-wiki/run.py -m tools.lint --wiki-dir wiki --config .alpha-wiki/config.yaml --dry-run
```

The launcher keeps dependencies in `.alpha-wiki/runtime/.venv`, outside the
product environment. First setup or a changed runtime manifest needs `uv`;
a prepared runtime can be reused without `uv`. Product manifests stay unchanged.

Codex project hooks are defined in `.codex/hooks.json`. Review and trust them with `/hooks` after init or an Alpha-Wiki upgrade.

## Native Subagents

Use Codex native subagents only for independent, material scopes:

- Prefer read-only exploration, audit, source analysis, and summarization.
- Choose the smallest useful number of independent subagents; one helper is valid.
- The controller records one pinned repository/SHA snapshot before fan-out; for
  dirty worktrees use `python3 .alpha-wiki/run.py -m tools.worktree_snapshot --root . --json-output`.
- Give every subagent a bounded scope, explicit non-scope, permissions, evidence format, and terminal status.
- Do not let subagents independently refresh shared remote refs or create nested subagents.
- Parallel writers must have disjoint files; a shared file has one writer per wave.
- Wait for every agent to reach a terminal state, then deduplicate and synthesize in the main task.
- Keep deterministic `doctor`, `lint`, `status`, `render`, and `rollup` backends in the main task.

Follow `references/codex-subagent-orchestration.md` when it is available.

## Optional AgentOps

Use `$alpha-wiki:orchestrate` only when the user asks for controlled,
multi-track delivery. AgentOps state lives under `wiki/agentops/`; it is not
part of normal initialization or the first-run path. The controller owns the
plan, deterministic checks, conflict resolution, and final synthesis. Native
subagents receive bounded scopes and write summarized session evidence rather
than raw logs.

Follow `references/agentops-control-layer.md` when AgentOps is enabled.

## Shared Contract

Read `.alpha-wiki/config.yaml` for the authoritative page schema and cross-reference rules. This `AGENTS.md` is the shared human-readable operating contract for every supported agent runtime.
