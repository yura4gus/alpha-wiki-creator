# Alpha-Wiki Instructions

This repository uses Alpha-Wiki as its durable markdown memory layer.

## Start Here

1. Read `wiki/graph/context_brief.md` before substantial project work.
2. Use the wiki to recover project purpose, boundaries, contracts, decisions, risks, and gaps.
3. Cite source wiki pages when an answer or implementation decision depends on project memory.
4. Run `uv run python -m tools.status --wiki-dir wiki` when the current state is unclear.

## Mutability

- `raw/**` is source evidence. Do not rewrite it during normal agent work.
- `wiki/**` except `wiki/graph/**` is maintained markdown memory.
- `wiki/graph/**` is generated by deterministic tools. Never hand-edit it.
- `.alpha-wiki/config.yaml`, `CLAUDE.md`, `AGENTS.md`, `.claude/**`, and `.codex/**` are the runtime contract. Change them deliberately.
- Preserve bidirectional wikilinks and run lint after wiki edits.

## Codex Workflows

Preferred plugin invocations use the `alpha-wiki` namespace:

- `$alpha-wiki:init`
- `$alpha-wiki:doctor`
- `$alpha-wiki:ingest`
- `$alpha-wiki:query`
- `$alpha-wiki:lint`
- `$alpha-wiki:evolve`
- `$alpha-wiki:status`
- `$alpha-wiki:spawn-agent`
- `$alpha-wiki:render`
- `$alpha-wiki:review`
- `$alpha-wiki:rollup`
- `$alpha-wiki:audit-project`
- `$alpha-wiki:orchestrate`
- `$alpha-wiki:backlog`
- `$alpha-wiki:handoff`
- `$alpha-wiki:release-check`


Standalone compatibility skills use `$alpha-wiki-<operation>` only when the
plugin surface is unavailable. Do not install both surfaces together.

Project-local deterministic tools remain the source of truth:

```bash
uv run python -m tools.doctor --project-dir . --platform codex --refresh
uv run python -m tools.status --wiki-dir wiki
uv run python -m tools.lint --wiki-dir wiki --config .alpha-wiki/config.yaml --dry-run
```

If `uv` is unavailable but the project environment is already installed, use `.venv/bin/python` instead.

Codex project hooks are defined in `.codex/hooks.json`. Review and trust them with `/hooks` after init or an Alpha-Wiki upgrade.

## Native Subagents

Use Codex native subagents only for independent, material scopes:

- Prefer read-only exploration, audit, source analysis, and summarization.
- Default to two to four subagents; use more only when requested or clearly justified.
- The controller records one pinned repository/SHA snapshot before fan-out; for
  dirty worktrees use `python -m tools.worktree_snapshot --root . --json-output`.
- Give every subagent a bounded scope, explicit non-scope, permissions, evidence format, and terminal status.
- Do not let subagents independently refresh shared remote refs or create nested subagents.
- Parallel writers must have disjoint files; a shared file has one writer per wave.
- Wait for every agent to reach a terminal state, then deduplicate and synthesize in the main task.
- Keep deterministic `doctor`, `lint`, `status`, `render`, and `rollup` backends in the main task.

Follow `references/codex-subagent-orchestration.md` when it is available.

## Optional AgentOps

Use `$alpha-wiki:orchestrate` only when the user asks for controlled,
multi-track delivery. AgentOps state lives under `wiki/agentops/`; it is not
part of normal initialization or the first-run path. The controller owns the
plan, deterministic checks, conflict resolution, and final synthesis. Native
subagents receive bounded scopes and write summarized session evidence rather
than raw logs.

Follow `references/agentops-control-layer.md` when AgentOps is enabled.

## Shared Contract

Read `.alpha-wiki/config.yaml` for the authoritative page schema and cross-reference rules. If `CLAUDE.md` contains the generated Alpha-Wiki contract, use it as the shared human-readable view for Claude Code and Codex.
